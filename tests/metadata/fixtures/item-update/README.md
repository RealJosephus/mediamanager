# Item update oracle

`Program.cs` executes the pinned Jellyfin DLL's public `ItemUpdateController.UpdateItem` using its actual `BaseItemDto` JSON converters and localization resources. The library persistence and provider refresh callbacks are recorded proxies. Physical children come from `input.json`; local alternate versions and collection folders are empty. This verifies field binding, mutation, child propagation and repository callback order. It does not claim real native database, NFO, HTTP authorization, concurrent writes or network failure equivalence.

Generate the schema and recording through `tools/validation/oracle.js`, in separate new isolated output directories, passing `schema {output}/schema.json` or `tests/metadata/fixtures/item-update/input.json {output}/native.json`. Use the configured isolated baseline DLL and .NET toolchain. Copy only successful outputs. `provenance.json` seals the source, common build properties, input, schema and native output, along with the tool and DLL identities. Retain original recording directories containing build/run output and `record.json`.

The candidate consumes these recordings in `tests/metadata/item-update.test.js`. The separate `tests/http/item-update.test.js` uses SQLite, real PostgreSQL and a versioned VFS fixture to exercise HTTP authorization, native relation storage, NFO output, lock propagation, conflict rejection and compensation. Its fixture backend does not establish production atomicity for AList or WebDAV. People are staged with their item's metadata and files to obey the network storage failure contract; native pre-item people commits during later failure remain a separate difference to verify.
