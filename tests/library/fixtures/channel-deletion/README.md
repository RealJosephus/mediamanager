# External Channel deletion consumers

The oracle executes the supplied assemblies' actual `ChannelManager`, typed
`BaseItem` virtual deletion methods, `DtoService` list and detail consumers,
`LibraryController.DeleteItem`, `LiveTvController.DeleteRecording`, and
`LibraryManager.DeleteItem`. A fresh component-owned SQLite database uses the
actual repository and `ItemPersistenceService`; it is not a production database
import or a migration acceptance test. The current SDK RID's packaged SQLite
image is loaded by absolute path, installed as the provider's explicit native
resolver, and recorded with its SHA-256 and runtime identifier. All managed
assembly identities, the exact input bytes and source bindings are recorded.
Both consumers use the native default case-sensitive item IDs. The input
document preserves explicit nulls, including the original nullable ExternalId.
The PostgreSQL graph copies the actual EF BaseItems rows before each observation,
including its real placeholder seed, and final row comparison retains that seed.

Provider permission and deletion methods are controlled. Only the fixture's
owned external identifier (or its explicit null case) reaches them. Native
`CanDelete` is synchronous; the Node SDK permits an asynchronous callback and
awaits it at the same consumer boundary. Provider lookup uses registration
order and the referent's own ID, without the Features name fallback. Native
empty/missing referent behavior, marker absence, duplicate identity selection,
provider failure, active Video exclusion, root Channel/Folder overrides,
physical MusicArtist behavior and BoxSet/Playlist user authorization are kept
as separate observations. A warm entity name proves the provider receives the
actual cached object without saving that edit. List DTOs use the native
precomputed folder overload; detail DTOs use the native virtual user overload.
Native deletion records the actual `CancellationToken.None.CanBeCanceled`.
The Node record separately observes its real plugin-scope AbortSignal; the
comparison does not label that activation signal as a CLR noncancellable token.

The active-recording association callback is an explicit read-only control
after the actual Video permission gate. User-data dependencies are read-only
controls. No recording, tuner, stream, media probe, catalog fetch or encoder
executor starts. The controller cases call actual action methods with controlled
principals; this component does not claim a native MVC host or authorization
middleware differential.

Deletion cases use real owned source and metadata bytes. Actual provider
deletion precedes metadata cleanup, EF deletion and removal events. Native
`ArgumentException` and the `ArgumentNullException` derived case continue
cleanup; I/O and other failures retain the uncommitted prefix. External source
bytes must survive every external deletion. The Live TV action deliberately
has a provider permission callback that would fail if evaluated, proving that
its management deletion performs visibility lookup without consulting
`CanDelete`. SQL rows, parent cache invalidation and event state are hard
assertions, including every declared native success.
Expected public 500 diagnostics retain the exact installed provider entry path,
source SHA-256, exported throw line and original Error stack, and compare wire
status, CLR exception name and message to the actual native action. V8 may omit
the asynchronously awaiting deletion frame from that original stack. A separate
read-only synchronous observation on the admitted operation therefore records
the real ItemDeletionService call line, item and nullable external identifier;
the provider failure is bound to that same observation. The observer returns the
original promise and does not catch, replace or modify the provider error.
The actual user controller's denial retains all rows and bytes before external
deletion. The actual batch controller deletes its first requested item before
returning 404 for the following missing ID; the Node public batch route must
preserve the same committed rows, cleanup and event prefix.

The Node side creates a fresh PostgreSQL schema and installs the controlled
package through the actual PluginHost/SDK. It uses real typed hydration,
ItemCreationService, ItemDeletionService, ExternalDataManager, mapped Local I/O,
DomainStore writes and public HTTP DELETE routes. Direct DTO comparisons bypass
visibility on both sides so they isolate the actual DTO overloads; standalone
visibility has its separate native differential. The public action comparisons
perform the actual production lookup and deletion. An explicit external-data
directory declaration is controlled; the cleanup service and file operations
remain real. Nothing deletes caller or production media.

The held HTTP cases are Node integration evidence. A real provider permission
callback pauses a selected `CanDelete` Items DTO or a DELETE request, then
Channel close and metadata cancellation begin. The admitted DTO must still
complete; deletion permission and execution must reuse one operation, with the
SQL deletion and event finishing after the gate opens. A transport abort does
not cancel the admitted provider deletion. New operations reject, all existing
operations drain, and relation states/cohorts must be released before closure.
These cases do not claim a matching full native HTTP host.

Only `componentAcceptance` can become true after every hard assertion and
comparison succeeds. Phase and final release acceptance remain false. External
latest/catalog execution and unexercised native deletion shapes remain separate
release responsibilities.
