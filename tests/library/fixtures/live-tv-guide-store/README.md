# PostgreSQL guide program batches

This component uses actual PostgreSQL, the shared typed entity factory/cohort, `LibraryService`, metadata context loader, `MetadataUpdateHost.runMetadataSavers`, `ItemCreationService` setup and `persistMetadataInDatabase`. It compares repository state and observed execution boundaries; it is not a new actual native DLL oracle. The separate `live-tv-guide-program` fixture executes actual private native `GetProgram`/`GetChannel`. Batch ordering here follows actual `GuideManager.RefreshChannelsInternal`, `LibraryManager.CreateItems`/`UpdateItemsAsync` and the existing shared native insertion-order implementation. Existing array `createItems` is used only for bounded fixture setup, outside the new production path.

The production batch owns one nontransaction TEMP session plus a retained SQL typed cohort. Its initial membership/full BaseItems snapshot, ID-to-slot dictionary, seen identities and new/updated occurrences stay in PostgreSQL. Candidate/occurrence SQL transfers never exceed 128; materialization and saves hydrate one owned entity at a time. New duplicates remain separate slots and never enter the initial dictionary. Existing repeated IDs share the same mutable slot. Final persistence chooses the last slot per ID in the first ID's occurrence position inside SQL. New IDs are globally ordered across the complete transaction, not independently per page.

Tests cross 128 with 131 distinct programs, repeated new/existing IDs, delayed save until all materialization succeeds, per-occurrence real savers and two DateLastSaved writes, a final null-genre failure, a later-page PostgreSQL CHECK failure with complete BaseItems/provider/image/value-map rollback, and cancellation after metadata saver prefixes. A configured controlled saver for an existing mapped media path executes through the actual metadata update host with no request token, writes a real VFS memory file before the final transaction, and retains that file when cancellation prevents the repository save. Runtime slot/view rows and TEMP tables are checked after normal/failing owners release. Synthetic programs normally have no media path, and transient program images under a live-TV channel take the existing native image skip branch. This fixture does not claim full external saver/native file-format or raw-stream/guide orchestration coverage.

`withGuideProgramBatch(options, operation)` owns the callback. Consume serially, seal, saveNew, precache the retained newView, saveUpdated, then precache retained updatedView. Each view getter returns one owned reference that the caller must release; it can outlive the TEMP callback if retained. `seenPlan` is valid only inside that callback and must be copied to another SQL owner before exit when needed. Sealing does not save. A materialization failure prohibits later sealing/saving while leaving earlier seen identities available to the owning callback. Metadata savers run without the request cancellation token before the final updated transaction observes cancellation.

Run only through authorized Actions validation. No recording, scheduling or media executor starts. PostgreSQL rollback verification, the separate native materializer differential, orchestration, phase acceptance and release acceptance are distinct evidence scopes.
