# Current item cache consumers

`current-profile.json` binds the existing neutral input and the current driver,
project and shared build properties. `native-item-cache.test.js` records the
supplied designated Native runtime during the same Actions run. The input copy,
Native JSON, source copies, assembly identities, build logs and process receipt
remain in the isolated validation output.

All 40 scenarios and 2,428 ordered operations remain covered: four invalid
capacities, 29 entity registrations and seven mixed lookup/update/removal
sequences. The real LibraryManager provides constructor failures, returned
values and repository fallback observations. A separate cache from that same
runtime consumes the same operations using IDisposable values; the candidate
compares released resource identities and multiplicities after each operation.
Release enumeration order is irrelevant. Both caches must remain bounded.
Invalid capacities must be rejected on both sides; exception class names remain
diagnostic observations.

The candidate also loads all registration types through PostgreSQL, removes
their rows, and compares returned names against the same-run LibraryManager
result while retaining the requested item ID and entity type.
Queue partitions and resident enumeration are not consumer observations.

The historical input, driver, project, README, Native recording, provenance and
absolute recording references remain byte-for-byte intact. They preserve the
earlier evidence; current execution uses the new driver. SQL/file deletion,
native authentication, clients and instance exchange are outside this fixture.
