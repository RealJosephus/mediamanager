# Existing recording directory readers

`Program.cs` executes the selected build's actual `RecordingsManager.GetRecordingFolders`, `LiveTvManager`, `LibraryManager` and EF SQLite `BaseItemRepository`. It first copies the designated stopped instance's SQLite bytes into an owned private database. It does not call `EnsureCreated` or apply migrations: those produce a schema which can differ from the pinned migrated schema. It records source/copy SHA-256 and the actual `sqlite_schema` plus migration history, clears only the private library graph, then creates controlled rows, parent/ancestor relations, genres and real isolated directories. Schema and migration history must remain identical after the EF writes, and the original supplied bytes must remain unchanged. Node runs its unchanged strict schema and migration-history preflight before importing the exact repository rows into PostgreSQL and invoking the real `LiveTvRecordingsService` and `LibraryService` query/DTO path.

The native generic DTO builder is a declared control: it projects identity, name, kind, optional tags and four removable fields from the actual manager's DTO options after its query. Comparison uses only that same subset of the Node's actual DTOs. Full native generic DTO construction, all permissions and HTTP binding are separate consumer scopes. The empty `IChannelManager` control records both refresh-latest true/false calls; it does not implement or validate an installed external Channel provider, plugin enablement, provider refresh or dynamic streams.

Cases cover directory deduplication, newest exact-path source selection, cultural recording-folder order, video/nonvirtual/ancestor filters, owned and alternate suppression, presentation-key grouping, type include/exclude precedence, sports/kids genre union, ignored bound selectors, counts/offset/limit, userless reads, explicit in-progress reads without a recording executor, removed DTO fields, and a response spanning bounded SQL pages. An additional real PostgreSQL owner check changes a live row after capture and proves the later page retains the captured value. It verifies every page stays at most 128 rows and that the temporary table is released. Full business rows remain read-only after normal queries.

Recording-folder order has two explicit preparation lanes. The original native lane assigns controlled live objects to `UserRootFolder.Children`, preserving their manually assigned raw `SortName` cache (`Recording 10` precedes `Recording 2`). It records those `warmFolderIds` and each stored/live sort value. The second lane resets the fixture-owned library cache and obtains a new root with actual `LibraryManager.GetItemById` / `BaseItemRepository.RetrieveItem`, leaves `Children` unassigned and lets real `UserRootFolder.LoadChildren` / `Folder.GetCachedChildren` hydrate its rows from SQLite. Actual `BaseItemMapper` assigns `SortName` before `ForcedSortName`; the latter setter clears the cached name even for null, so live alphanumeric keys are recomputed and `Recording 2` precedes `Recording 10`. Both lanes call the same real `LiveTvManager.GetRecordingFoldersAsync`.

The default Node resolver compares with that actual cold repository lane. A separately declared warm control wraps its real `LibraryService.load`, assigns the same explicit input sort values to the freshly hydrated typed children, and installs them through the existing authoritative `setFolderChildren` cache. The real resolver, collection membership and PostgreSQL cultural sorter still execute; the control neither substitutes a result nor changes stored rows. Its result and raw stored/live keys compare with the original native warm lane. The report retains both consumer states, and the test proves the input distinguishes them and that PostgreSQL business rows remain unchanged. This is component preparation evidence, not a claim that a production cold load preserves a different process's warm object cache.

The same current DLL also measures retained `MediaBrowser.Controller.Channels.Channel`, which is distinct from a tuner `LiveTvChannel`: its constructor, complete serializable property metadata/order, raw JSON, actual mapper fallback and persisted-column overlays, repository `SkipDeserializationForBasicTypes`, and `CanDelete=false` are compared with Node. Cases include SQL/JSON null, valid inherited folder/base fields, duplicate keys, whole-object fallback after malformed fields/root, and skipping valid/malformed JSON. Real PostgreSQL `mm_safe_native_item_data` consumes the exact Channel discriminator and source bytes, proving the typed SQL contract is present. The Channel entity always reports `SourceType.Channel`, including an empty `ChannelId`. This validates retained entities only; external Channel provider execution, refresh, media sources and permissions remain outside this component.

Nullable recording-folder users now execute the actual manager against controlled rows in its real SQLite repository. Sixteen cases cover null/empty/missing/default/empty-directory sources, Folder, UserRootFolder, UserView, legacy/managed BoxSet, Channel, enabled/disabled CollectionFolder and private/shared Playlist. The actual private `ExceptionMiddleware.GetStatusCode` maps the observed exception; the fixture does not invent status expectations. Each source/configuration preparation is explicit and restored before the resulting database is imported. Node applies the same captured mapper frame to PostgreSQL, uses real configuration XML and mapped directory observation, then runs the actual resolver; reads leave that prepared frame unchanged and every temporary preparation is restored afterward. An ordinary source invokes the explicit null-user guard (400); Channel/enabled CollectionFolder/shared Playlist dereference the missing user first (500); disabled CollectionFolder can skip to a later physical Folder (400) or the final provider-root user dereference (500). No physical source also reaches the latter 500. UserView does not implement ICollectionFolder and reaches the ordinary 400 guard. Both BoxSet forms validate the parental user before linked-item evaluation.

The actual `BaseItem.EnableMediaSourceDisplay` / `ChannelManager.EnableMediaSourceDisplay` getter is also captured with an explicitly empty provider inventory. Empty source ChannelId fails with native ArgumentException/400; nonempty missing and wrong-type IDs return true because the provider predicate is never evaluated. Ordinary library-source items return true without a channel lookup. Node compares these cases across the original typed entity, clone and SQL-state capture/restore and proves unselected DTO fields and plain object copies do not evaluate the deferred getter. A complete DTO independently resolves ChannelName at the end of AttachBasicFields even when the display field is not selected; that lookup still rejects an empty source ChannelId. The separate `channel-static-media-sources-native.test.js` calls actual DtoService to distinguish these two consumers, including absent and wrong-type channel references. The getter is excluded from persisted private state and retains its constructor behavior after restoration. A nonempty provider inventory and `IDisableMediaSourceDisplay` producer are still outside this retained-data slice.

Five actual `CanDelete` cases also execute the real empty `ChannelManager`
inventory for file, remote, pathless and wrong-type channel references, plus the
Channel entity override. Without an `ISupportsDelete` provider the result is
false. The same five inputs also execute actual DtoService with CanDelete
selected for userless and user consumers, retaining either its value or its
complete exception/status/stack. In particular, the Channel override returns
false independently, but a complete DTO with an empty ChannelId fails in the
separate final ChannelName lookup before it can return CanDelete. Node compares
these distinct consumers; successful native DTO lanes must not conceal missing
dependencies. A provider-backed delete operation is outside this component.
Nullable source preparations translate the captured CLR GUID values to the
database's uppercase D format before applying them to the existing PostgreSQL
rows. The supplied raw rows and the restored final graph remain unchanged.

`live-tv-recordings-close.test.js` pauses actual service directory observation, replaces the named configuration through real XML I/O, starts close, and proves admitted readers drain while later scoped lookups see the current cache. Released scopes and new work remain unavailable. This is a lifecycle integration test, not native timing evidence.

`tests/http/live-tv-recordings.test.js` checks retained route binding and the real `AuthenticationService` access/management distinction with controlled authentication identities. Its PostgreSQL integration composes the action with actual item hydration, deletion, metadata cleanup, source retention and removal events, including an ordinary Audio item whose `CanDelete` is false. It does not claim a real native HTTP authorization or DTO comparison; that remains an independent acceptance scope.

Inputs and results are generated under the authorized validation output directory. The report binds native input bytes, executing assemblies and build source files; the private SQLite database/directories are removed after Node closes. No recording scheduler, recorder, tuner, stream or encoder is started. This component does not establish phase or release acceptance. Run only in the authorized Actions workflow.

The oracle requires the designated Jellyfin runtime's SQLite native image for the
current SDK RID. MSBuild copies that exact platform file into the isolated oracle
output and fails if it is absent. The process reads and hashes the copied image,
loads its absolute path and binds the SQLite provider's native imports to that
handle before `Batteries_V2.Init()`. It records filename, runtime identifier, bytes
and SHA-256 in `nativeLibraries`; a host-system SQLite fallback cannot satisfy
this fixture.
