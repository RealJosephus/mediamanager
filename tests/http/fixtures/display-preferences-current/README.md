# Current-run DisplayPreferences observations

This fixture replaces the executable historical closure used by the two current DisplayPreferences tests with observations from this workflow's designated Jellyfin build and stopped native instance. The old `../display-preferences` recordings, seals, recorder projects and provenance remain unchanged. No old `native.json`, expected DTO, old recorder DLL, build log or execution receipt supplies a new output.

`input.json` is the byte-identical copy of the old **request and setup input**, SHA-256 `133a711f5a0c451e43cafefae2a261da6dbfb6e3c53604892e8f75a6f74da327`. It retains all 119 scenarios and 126 HTTP requests, including typed binding failures, authorization, identity/client scopes, accumulated home sections, controlled database failures and independently committed write prefixes. `../display-preferences/observations.js` is reused as pure comparison code: complete HTTP status/content type/Allow/body or JSON and all typed columns of the four preference tables remain compared; only request trace IDs and Allow ordering are projected.

`capture.js` obtains `currentNativeReference()` and hashes the stopped database, input, executing build sources and loaded assemblies. Each mode builds and runs `Program.cs` through the common `recordOracle` in two new independent output directories. Original build/process logs, output JSON, recorder sources/assembly identities, source bindings and actual SQLite library identity are retained under `display-preferences-current-{http,snapshot}-<uuid>`. Both runs must match, their source schema/history must be preserved, and the protected inputs must remain unchanged even when an observation fails. A failure is cached for that worker rather than replacing its evidence with a retry.

After the recorder process returns, `finally` removes each private `states` directory on both success and failure. It verifies the fixed owner/child absolute paths, real paths and every entry's lack of links before recursive removal, and asserts the private directory is gone. Only database clone hashes, schema/history digests, controlled preference rows and original process evidence remain; raw database copies and their SQLite free pages are never intentionally uploaded. Cleanup failure is a hard failure and cannot produce phase acceptance. This phase flag proves the repeated native observation only; the separate PostgreSQL test assertions determine candidate equivalence.

The `http` mode hosts the actual MVC `DisplayPreferencesController`, JSON/query binders, default authorization handler, exception middleware, `DisplayPreferencesManager` and EF SQLite. Authentication principals and the user/local-network lookup boundary remain explicitly controlled, as in the original component fixture. Every scenario clones the supplied stopped database bytes into its own new private file, clears data and integer sequences, preserves the actual migrated schema/history, inserts the same two fixed users and applies the input's setup SQL/failure trigger. It never calls `EnsureCreated`, changes the supplied instance or starts a native background server. All manager connections enable foreign keys. Every request and each committed-state snapshot are recorded before host shutdown/disposal.

The `snapshot` mode calls the actual controller and manager with an explicitly controlled principal. It commits a display/home change immediately before the first item-preference lookup, records the response's earlier captured values and the later committed read, and preserves all four tables before/after. The PostgreSQL runtime test still holds the corresponding real SQL phase and compares the same observations, then verifies the next request sees the committed values. The other real runtime authentication/API-key/restart/close/page/snapshot tests remain unchanged.

The PostgreSQL differential still runs each of the 119 scenarios against a fresh real PostgreSQL schema and production HTTP application. Its initial preference rows come from that same-run native setup snapshot; it compares complete final rows and every HTTP observation. This is a component HTTP/read-write contract, **not** evidence that SQLite-to-PostgreSQL production import ran. The separate existing `display-preferences-exchange.test.js` retains the real production import/export and actual native database-consumption scope. Native media execution, recordings, encoding and background Guide tasks are not started by this fixture.

Actions must provision `native_reference=true`, `native_instance=true` and PostgreSQL. The two test consumers declare `dotnet`, `jellyfinDll`, `nativeInstance` and `postgres`; no historical private path is required. Add `native_sqlite=true` when also selecting the existing exchange test, which has its own actual SQLite supply. Select `tests/http/display-preferences.test.js` and `tests/http/display-preferences-runtime.test.js` (plus the exchange test for joint regression) with the existing strict validation runner. Run the exact selection on Windows, Linux and macOS; no local validation was performed during this change. The report's phase acceptance covers only these new observations and independent repeats; release acceptance stays false.

Behavior sources are the designated Jellyfin controller, manager, DTO, authorization/middleware, API registration, database context, four preference entities and enums listed in `capture.js`; each source hash is checked against the current build's source manifest. The fixture uses those runtime assemblies under the project's existing license terms; the repository LICENSE remains applicable.
