# Saved Live TV timer HTTP consumers

`../../live-tv-timers-native.test.js` uses the current designated native build and its stopped controlled instance. No historical HTTP response is replayed. Source bindings name the actual controller, manager, timer managers, entity models and DTO models in the executing build manifest.

The native side has two real process lifetimes. The first receives empty `timers.json` and `seriestimers.json` before startup. A real user-view request discovers the configured global Live TV identity; the test waits for that exact row's non-MinValue `DateLastRefreshed` commit before collecting read-only snapshots. After empty-list/default/error requests and clean shutdown, the stopped private SQLite database receives controlled channel, program, Series, ancestor and image rows. Both timer documents are then populated before the second native process starts. The native timer managers and startup behavior run unchanged. All timer dates are tied to the current run's real clock, strictly in the next one through six days, with full 100ns fractions; no timer is due during the test and the timer duration remains below the native scheduler's approximately 49-day limit.

Each Node stage creates a new PostgreSQL schema, copies the stopped private native media rows and relations with the same insertion order, and writes the same original timer bytes before its first `createRuntime`. An explicit absent-state assertion precedes runtime construction. Only the ordinary runtime `initializeLiveTvState` imports the timer documents; the harness never replaces or constructs the authoritative PostgreSQL timer state. This is real PostgreSQL/runtime/HTTP evidence, not a production entry or CLI import acceptance claim. Instance paths are rebased only for the controlled Node copy. Image rows point to the same actual private PNG asset on both sides, preserving the identity used by image cache tags; dimensions come from that PNG's header. The test covers image selection/tag/association fields and does not claim image endpoint pixels.

Requests cover anonymous/invalid/ordinary/disabled-Live-TV/admin/API-key authorization; empty and nonempty timer/series collections; New, InProgress, Cancelled, Error, ConflictedOk and retained Completed state; active/scheduled/channel/series filters; native GUID query forms; ignored unbound paging/user/field selectors; stable name/numeric/priority ordering; string-detail identities and missing/invalid/whitespace paths; and Defaults with missing, malformed, wrong-type, missing-channel and foreign-service program inputs. Full HTTP status, content type, JSON or original non-JSON/empty body and order are compared. Only actual trace IDs and equivalent date spelling are projected; UTC presence and full ticks remain checked.

Channel links, `ProgramInfo`, record status overrides, shared Series/program/channel image tags, daily/weekly patterns, constructor defaults and padding are exercised by these actual HTTP readers. The full before/after/closed database and document snapshots are retained per side. Read-only media/UserData/permission/preference/relationship tables must remain unchanged; the Node control-state string must remain unchanged. Final Node state is captured after HTTP/background owners close, immediately before the database owner closes.

After the populated read matrix, only the Node source documents change to empty bytes. Warm reads and a real runtime shutdown/reopen must still return the original PostgreSQL business state. This deliberately demonstrates ordinary read authority. It does not claim that a state package can be captured successfully from mismatched source files; the separate state-package contract rejects that mismatch.

Every actual HTTP observation, per-request Node runtime errors, original source bytes/SHA, SQL state, view commit row, private image identity and process/port/schema/input cleanup is retained through the credential-filtered private-output workflow. The zero-GUID Defaults request throws a domain error that the production middleware reports before returning 400; its exact error is checked separately from successful and binding responses, which must report none. Syntax, runner and HTTP execution occur only in three-platform GitHub Actions. This fixture provides no tuner/listing/recording execution, complete clients, complete Live TV, production-scale or release acceptance evidence.
