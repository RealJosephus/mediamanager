# Current library structure consumers

`library-structure.test.js` runs the 102 HTTP cases and 15 collection markers from the original input against two independently built and executed current designated Native consumers. The new neutral input retains every original request, permission case, malformed body, manager failure, rename conflict and second-move failure. Additional nested UTF-8 and binary files make loss, truncation and partial rename results observable.

The Native consumer uses the actual `LibraryStructureController`, MVC binders, permission handlers, `Directory.Move`, `CollectionFolder` options methods and `MyXmlSerializer`. Principals, network decisions, library-manager requests, provider refresh requests and shortcut creation are controlled seams. This is component HTTP and file-consumer evidence, not a complete Native instance or database exchange.

Each run retains its input, build/source receipt, assembly identities, HTTP bodies, manager requests, options events, paths, full file bytes and snapshots after attempted moves. Comparisons use each run's actual root and bind temporary paths to their recorded file operations. Final directory names and file contents, injected operation failures, complete public responses, manager input values, options events and cold options reads are compared. Consumer refresh requests preserve their item IDs and functional settings. Scheduling traces, delay values, transient names and exception diagnostics remain in the raw observations.

Library rename and subsequent media-path editing and removal share the host filesystem's single-segment validation. The direct physical-filesystem component retains all original cases, including literal Unix colons, backslashes, trailing dots and spaces. Windows rejects names that its path normalization changes. The separate PostgreSQL runtime lifecycle follows a renamed folder through path editing and deletion while preserving source media; its positive name also satisfies the configured VFS and local adapter namespace. It retains the public omission of the item ID after rename, then scans and compares all persisted options before deletion. On Unix, that lifecycle uses a trailing dot and space to exercise the former validation failure. It does not establish runtime support for names rejected by the storage namespace. The current Native snapshot preserves literal filename characters instead of rewriting every backslash as a directory separator. After all file consumers finish, trees containing names that GitHub artifact transport cannot carry are stored as verified gzip JSON archives with every original relative path, directory, file byte count, SHA-256 and complete bytes. Archive receipts identify the original roots; only those already archived isolated trees are removed before upload.

Node executes the real `LibraryConfigurationService` for rename and `LibraryOptionsStore` for options persistence, using physical files and the local storage adapter. Its observations are retained before assertions. The original two-move failure keeps the first committed directory contents and the failed destination in the resulting file tree. The fixed destination's files must remain intact.

The final test reads every successful Native-written `options.xml` through a new Node options store. It then passes every Node HTTP-written options file to the current Native `MyXmlSerializer` and `CollectionFolder.GetLibraryOptions`, applies the neutral continuation through `CollectionFolder.SaveLibraryOptions`, and reads the result with another new Node options store. Full options values and public update events are compared throughout; XML bytes before and after each consumer are retained. XML layout is accepted only with these real readers.

The current entry has 105 test registrations: two current-input/marker tests, 102 HTTP cases and one options continuation test. It requires `dotnet` and `jellyfinDll`; the independent existing PostgreSQL runtime and options-store suites retain their own scope. All execution belongs in the Windows, Linux and macOS Actions jobs. The historical `library-structure` fixture, including input, raw observations, provenance, sources and README, remains unchanged.
