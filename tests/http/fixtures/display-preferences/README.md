# Display preference HTTP and persistence fixture

The recorder executes the designated workspace's `DisplayPreferencesController`, MVC JSON/query binders, authorization handler and exception middleware, `DisplayPreferencesManager`, and EF SQLite. Authentication principals and local-network/user lookups are controlled. The two persistent users have fixed IDs. Each scenario uses a new SQLite database. Database triggers inject failures into real persistence operations.

`input.json` defines requests, repeated operations and initial SQL. `native.json` preserves the original recording bytes. `provenance.json` binds designated source files, their isolated build copies, recorder inputs, the actual loaded assemblies and SQLite library, and an independent repeat. Complete reference-build input closure and full product acceptance remain unproven.

The 119 scenarios (126 HTTP requests) cover defaults and GET writes, MD5/Guid identities, user selection, client case, ignored DTO fields, nullable custom dictionaries, unknown and duplicate keys, enum/numeric conversion and numeric overflow failures, NUL/Unicode text, home-section accumulation, existing rows, and independent custom-delete/insert, item-update and display/home transaction failures. They include encoded slash casing, required route strings, malformed Unicode values/keys, and OrdinalIgnoreCase boundaries. The POST constructor defaults differ from the manager's GET defaults. A missing item preference is initially saved with Guid.Empty; GET changes only the detached entity. Display updates attach new home sections without removing existing rows. Custom dictionary deletion commits before replacement insertion, then item and display saves commit independently.

`observations.js` compares complete typed rows, row order, HTTP status, content type, Allow methods and lossless JSON values. Only request trace IDs and Allow method ordering are projected. Generated integer identities are compared directly in these deterministic fresh-database scenarios. The recorder's internal call list is diagnostic.

The candidate differential uses real PostgreSQL and the same initial preference rows; authentication is controlled at that boundary. `display-preferences-runtime.test.js` separately exercises real authentication, API keys, restart, shutdown admission/draining and 20,000 unrelated rows with 128-row relation pages. These do not establish complete native-instance, supported-platform or two-Web workflows.

`snapshot-native.json`, its provenance and the `snapshot` recorder bind an actual controller/EF read with a committed display/home change injected immediately before item lookup. An independent repeat returns the captured display and home values. Candidate reads preserve that phase with a read snapshot, then take a separate snapshot for paged custom values. Runtime tests also change all 300 custom values during page delivery, checking that one response does not mix old and new values. Neither read transaction changes the independent write-commit phases.

`display-preferences-exchange.test.js` prepares an empty isolated copy with the real native schema/history, performs authenticated candidate API writes, exports with the production exchange code, and runs the actual native controller/EF manager against the output. Native edits are reimported with all-table digests and a candidate cold read. It preserves NUL strings, prior home sections and unknown custom keys. The native source database stays unchanged. This limited database workflow does not establish a full-instance migration.

Behavior sources are the designated Jellyfin files, principally `Jellyfin.Api/Controllers/DisplayPreferencesController.cs`, `Jellyfin.Server.Implementations/Users/DisplayPreferencesManager.cs`, `MediaBrowser.Model/Dto/DisplayPreferencesDto.cs` and the four preference entities. Exact source paths and hashes are in provenance; applicable licensing is retained in the project LICENSE.
