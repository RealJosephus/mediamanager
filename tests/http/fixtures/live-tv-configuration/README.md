# Live TV named configuration HTTP consumer

`../../live-tv-configuration-native.test.js` starts the designated Jellyfin build from a private clone of the current stopped instance, and starts the Node production entry against a real PostgreSQL import of the same workflow's current native SQLite input. Both sides receive actual HTTP configuration POSTs. The test never mutates the Node cached configuration object or invokes its save method directly.

The requests cover authenticated GET and elevated POST, anonymous/invalid/ordinary-user authorization, complete replacement and defaults, exact property casing, ignored unknown subtrees, repeated tokens, quoted integers, nullable and string conversion, nested tuner/listing/channel-mapping fields, invalid earlier duplicates, invalid types/ranges, malformed/empty JSON, unsupported media types, and separately cached route-key casing. Recording fields are preserved; no recording or postprocessor is executed. All configured tuner/listing types are unregistered, recording paths are empty, and no media or external service is used.

Every successful save records the original native and Node file bytes, byte length and SHA-256. Copies of these exact bytes are read by the existing `tests/library/fixtures/live-tv-configuration/Oracle.csproj`, which uses the supplied native `MyXmlSerializer` and `ConfigurationHelper`. Typed native consumer values are compared; XML whitespace, BOM and element layout are not compared as raw equality across writers. Original bytes remain in the private run and the report. Live null collections may deserialize to constructor defaults after a cold XML read; live HTTP and file-consumer observations are recorded separately.

GET after save, Info, GuideInfo, user-view visibility/removal/restoration, and a real shutdown/restart of both application owners consume the saved configuration. The differently cased save demonstrates independent warm caches sharing one lower-case file, followed by cold reads of that file. Guide timestamps are checked against each request's adjacent actual clock samples, with exact day deltas, before projecting only that DTO's request-relative clock. Info users are checked against each side's real permissions and GUID order before mapping their established account names. The view consumer checks the global identity, path, English name and identity reuse; the existing dedicated user-view test retains the wider full-DTO/row/directory acceptance scope.

The report retains original request bodies, responses, content types, empty bodies, per-stage database/configuration-file snapshots, and the native XML consumer output. PostgreSQL media/user tables and imported Live TV state must remain unchanged for configuration saves and read-only Info/Guide requests. Failed requests also leave bytes/cache unchanged. User-view creation has separate before/after evidence because the read can create the retained global view. Both shutdowns capture database and file state, and process/port/schema/private-directory cleanup is required. Publication uses the shared credential filter and includes reports only.

For the first global Live TV view, the pre-request full native snapshot must have no row at the independently derived view ID. `LibraryManager.GetNamedView` queues that new view's initial refresh, `UserViewMetadataService` uses the base `MetadataService`, and `BaseItemMapper` stores `DateLastRefreshed` in the real nullable `BaseItems` column (MinValue maps to SQL null). The test waits for a non-MinValue stamp committed at that exact ID, checks the row type/path and response creation date, and binds the refresh/save clocks to this request and its subsequent SQL observation. The report retains the absent-before evidence, every sampled stamp/row hash, and the full completed row, including timeout diagnostics. Existing views do not take this wait. Node uses its actual view-owner drain. A quiet elapsed interval is not accepted as proof that the native refresh ran; this marker covers the new view's initial metadata commit, without claiming a global provider-queue drain.

The runtime `sourceBindings` verifies every named source against the actual executing build's immutable source manifest. This is fresh native HTTP/SQLite/PG/XML evidence, not a historical response fixture or an acceptance claim for external tuner/listings execution, recording, every named store, full clients, or production-scale release readiness. Tests, syntax checks and oracle compilation run only in GitHub Actions on Windows, Linux and macOS.
